4. Если известна лишь готовая duration, экспортируй её с указанием источника. Не выводи выдуманные start/end из времени сообщения. Не перепутай ms и seconds и не обрезай полезную точность.

### Этап 6. Исправить зависимости prep и порядок гейтов

**Prep:**

- Раздели подготовку мешающих существующих тестов и доказательство нового продукта. Убери blanket-зависимость всех agent lanes от всего prep.
- Зависимость вводи только для потребителя нужного результата; сохраняй реальный порядок конфликтующих записей.
- Inventory/test intent/fixtures существующих contracts готовы заранее; final behavior-cells validation — после появления его producers.
- В существующий validator добавь проверку отсутствующих/поздних входов стадий и циклических зависимостей по фактическим frozen WI contracts. Не строй отдельный универсальный планировщик.

**Гейты:**

- Введи минимальную декларацию типа входа `tree / candidate / build-output / deployed-service`, используя имеющийся формат/владельца конфигурации.
- Tree checks выполняются до публикации и связаны с проверенным деревом. Генерация до проверки; publish не правит/генерирует файлы.
- Candidate/build/runtime checks связаны с exact SHA, artifacts и target, не читают незаметно изменённый checkout. Сборка может быть до push при доказанной привязке.
- Не оставляй постоянную двойную проверку одним валидатором до и после publish без различия доказываемого входа.
- Дешёвый env/lifecycle contract probe обнаруживает lock/status/missing prerequisites до полного baseline набора. PLAN/base-probe не требуют ручного фиктивного перевода RUN в in_progress.
- PASS PLAN-probe переиспользуется в RUN только при существующих проверяемых условиях идентичности дерева, команд и окружения. Не пропускай пробу без такого доказательства.

**Проверки:** prep требует файл будущей зависимой lane; независимая lane стартует; overlapping writers сериализованы; tree-check только после publish отвергается; изменение inputs аннулирует evidence; недостающий live lock виден до дорогих команд; final validation ждёт producers.

### Этап 7. Сократить повторные тесты и стабилизировать live

- Сначала измерь и объясни selection/reuse: какие inputs расширили affected, какие previous failures потянули полный command, почему `commands_reused=0`. Не предполагай, что «несколько строк» означает узкое влияние.
- Внутри ремонта используй focus до устранения дефекта; один обязательный bound affected на выходе из целостной правки. Focus не становится доказательством полного gate.
- Переиспользуй PASS отдельных команд при доказанной неизменности всех влияющих inputs/environment/toolchain. Сохрани fallback на широкие проверки для неизвестного влияния и изменения safety-critical inputs.
- Уменьшай накопление изменений от старого dispatch baseline только через существующий доверенный механизм. Не позволяй кодеру менять baseline/evidence или забывать красные проверки. Ранее упавшая команда должна получить полноценное подтверждение исправления перед закрытием.
- Full final coverage обязательно; повторное исполнение каждого неизменившегося PASS не обязательно, если существующий доверенный контракт разрешает reuse.
- Тестовые scenarios/AC проектируются до кода. Воспроизводимые bug regressions — до исправления; concrete integration tests нового API — в собственной lane по заранее принятому contract. Не создавать helper-only PASS и не требовать зелёный тест отсутствующего будущего API в prep.
- Сохрани текущий механизм анализа повторяющегося defect_class и архитектурный checkpoint. Почини точечные обходы, если найдены; не добавляй ещё один счётчик/ревью-этап поверх работающего.
- Различай process runtime, setup/import/migration, resource wait и model gap. Не переносить все долгие shell в фон автоматически: это имеет смысл лишь при независимой runnable работе и поддерживаемой доставке результата.
- Live: attempt-owned disposable contour, fixture isolation и cleanup на успехе/ошибке; не очищай чужие данные. При повторном использовании ресурса очистка — предусловие; при новом namespace старый ресурс можно убирать независимо после проверки владельца.
- Не объявляй загрязнение базы доказанным без contour/attempt/fixture evidence. Сохрани отдельные tests commit/concurrency, не прячь их в rollback, который меняет проверяемое поведение.
- Раздели бизнес-deadline и test harness budget. Сначала profile/снижение конкуренции/перенос setup/разделение тяжёлых групп. При доказанно корректном медленном integration test допустим обоснованный test-budget; не увеличивай production deadlines или retries ради PASS.

**Проверки:** узкий assertion fix; прежний failed command; identical inputs reuse; unmapped change broad fallback; stale evidence reject; cleanup после сбоя; clean attempt после аварии; heavy/live wait отделены от выполнения; финальное покрытие сохранено. Используй существующие regression suites, добавляя только проверки существенных новых контрактов.

### Этап 8. Wake, compaction и достоверность продолжения

После upstream и инвентаризации устрани лишь подтверждённые оставшиеся дефекты:

- Unknown child не считается finished; отсутствие файла не даёт права перезапустить писателя того же артефакта.
- Wake учитывает существующие children/leases/gate locks и owner questions; сообщение не должно ложно утверждать, что детей нет.
- Исключи повтор wake из-за служебного изменения JSON, рестарта/повторного event или сброса дедупликации synthetic prompt. Минимально расширяй существующее persisted runtime state, если памяти недостаточно.
- Не вводи глобальную сериализацию ради wake: независимые runnable задачи могут продолжаться, пока ребёнок занят.
- Восстановление после compact читает authoritative state/evidence, approvals и leases. Короткая recovery summary выводится из них, не ведётся как вторая ручная база истины.
- Показывай requested/actual model и session reuse, когда сведения доступны. Fresh не называй resume. Reviewer fresh-policy сохраняется; reuse другой роли зависит от реальной поддержки runtime.
- Недоступность провайдера/лимиты — отдельная статистика, не причина ослабить review или автоматически поменять роль/модель.

**Проверки:** restart с running child; duplicate event; child unknown; owner question и background message; исчезновение tool/session; завершение ребёнка до установки waiter; новая независимая задача; восстановление после compact без нового owner decision.

### Этап 9. Удалить дубли инструкций и проверить итоговую связность

Это финальное сведение после локальной чистки каждого этапа:

- Проверь все места, перечисленные в DECISIONS.md; старые противоречащие правила удалены или заменены ссылкой на действительный источник.
- Общие authority/scope/foreground/evidence/context правила имеют одного владельца. Роли содержат специфику; самостоятельно запущенный агент получает обязательный контракт реально, не только гипотетически по ссылке.
- Нет единственного writable context-packet, автоматического RUN после approve, всеобщей prep-зависимости и одновременно разрешённых/запрещённых путей в разных профилях.
- Нет второго export formatter/timer/cache/approval store, если задачу решает имеющийся/upstream.
- Обнови документацию фактического поведения, а не планы как уже внедрённые функции. Сохрани требуемые RU/EN документы OpenChamber по стандарту проекта.
- Для удалённого code path есть доказательство отсутствия нужного внешнего потребителя либо сохранён адаптер с ясной причиной. Не делать общий cleanup несвязанного кода.

**Готовность:** итоговая таблица keep/merge/delete/upstream заполнена реальными diff; размеры/контекст до и после приведены без недоказанных token savings; примеры commands и effective permissions совпадают с runtime.

### Этап 10. Проверить интеграцию и передать ветки на независимое ревью

- Выполни нужные локальные проверки затронутых контрактов, pins/install generation и интеграционные regression checks между my-opencode и OpenChamber.
- После узких проверок выполни предусмотренные проектами итоговые полные проверки для фактически затронутых пакетов/систем. Повторяй только при изменении входов или объяснённом сбое. Не запускай полный SeVami suite только потому, что он упоминается в исследовании: при правке его harness проверь affected и обязательный итоговый профиль по правилам проекта.
- Покажи before/after выбор тестов, reuse и объём инструкций на сопоставимых входах. Отсутствие измерения честно укажи. Не выдавай synthetic benchmark за ускорение реального RUN.
- Подготовь пример полного Markdown с timing и дочерними calls; включи его путь в отчёт.
- Приведи cross-repo dependency: точные совместимые SHA, версии plugin/binary/server/UI, порядок будущей установки и rollback. Команды установки только запиши; production не обновляй.
- Сохрани commits; если доступно, non-force push feature-веток для чтения другим reviewer. Укажи remote URLs. Недоступность push явно отметь; локальный commit не выдавай за опубликованную ветку.
- Заверши статусом «готово к независимому ревью» только когда проверки завершены. Иначе «частично»/«блокировано» с точными пробелами. Владелец передаст отчёт другой модели, которая проведёт ревью веток. **Не merge в main и не публикуй релизы.**

## 5. Обязательный отчёт при каждом завершении

Сохраняй основной актуальный отчёт `project/pipeline-optimization-20261104/REPORT.md` и короткую запись о завершении в `project/pipeline-optimization-20261104/runs/<уникальный-id>.md`. Полный актуальный REPORT — один; запись запуска содержит его commit и дельту, чтобы история сохранялась без дублирования больших артефактов. Если у проекта есть подходящий существующий handoff формат, используй его, сохранив обязательные поля ниже.

**Не заканчивай одним обещанием продолжить. Отчёт нужен при успехе, частичном результате, блокировке, смене сессии и передаче работы.** При неожиданном аварийном обрыве следующий запуск сначала восстанавливает и дополняет отчёт по реальным commits/processes; не выдумывает завершённый прошлый шаг.

Шаблон:

```markdown
# Отчёт продолжения pipeline optimization 20261104

Статус: в работе / частично / блокировано / готово к независимому ревью
Дата и время, timezone:
Запуск/сессия, фактическая модель, если доступны:
Основной отчёт: <путь>

## Репозитории
| Repo | Рабочий каталог | Ветка | Base origin/main SHA | HEAD SHA | Remote branch URL | Working tree |
|---|---|---|---|---|---|---|

## Этапы
| Этап | Не начат / в работе / готов / блокирован | Что доказано | Commit / evidence | Что осталось |
|---|---|---|---|---|

## Сделано за этот запуск
- Конкретное изменение, назначение, затронутые файлы и commit.
- Какие существующие механизмы использованы вместо новых.
- Какие дубли удалены/объединены; где теперь каноническое правило.
- Upstream target versions/SHA, перенесённые/заменённые наши изменения.

## Проверки
| Команда | Каталог/окружение | Commit/input identity | Результат/exit code | Duration и источник | Evidence/log |
|---|---|---|---|---|---|

- Отдельно: не запускалось / не завершилось / невозможно проверить и почему.
- Не смешивать wall-clock, CPU, agent elapsed, tool duration и next-call estimate.
- Unknown duration или model/session: unavailable, а не догадка.

## Незавершённая работа и процессы
- Незакоммиченные изменения: точные файлы, чьи они, почему остались.
- Процессы/дочерние сессии: ID/PID с проверкой принадлежности, состояние,
  команда, рабочий каталог, лог/evidence, способ безопасной проверки завершения.
- Locks/resources: точный владелец/attempt, кто освобождает; не удалять чужое.

## Проблемы и решения
- Конкретный blocker, подтверждённая причина, предпринятые попытки.
- Что требует решения владельца, почему и какая работа независима.
- Provider/model limit: отдельно, без изменения архитектурных выводов.
- Отклонение от задания: что и почему; недоказанные гипотезы явно пометить.

## Продолжение
1. Сначала прочитать: <точные необходимые файлы>.
2. Проверить состояние: <конкретные refs/processes/tests>.
3. Следующее действие: <одна исполнимая команда или однозначная правка>.
4. Затем: <следующие зависимости/этапы>.
Не начинать повторный аудит уже проверенных неизменившихся областей.

## Передача на независимое ревью

- Краткая карта diff по целям задания.

```

В ответе владельцу при завершении кратко назови статус, завершённые этапы, ветки/HEAD, путь отчёта и следующий шаг. Не скрывай незавершённость словом «готово».

## 6. Условия итоговой приёмки

- ContextScout действительно пишет во всё согласованное planning-поддерево; дистрибутив не затирает это ограничением одним файлом.
- Сделан аудит использования решений, удалены подтверждённые дубли и противоречия, канонические источники реально загружаются.
- Upstream обновления выполнены в feature-ветках либо есть точный незакрытый blocker; заменённые обходы удалены с проверкой.
- PLAN не выдумывает поведение из неполного контекста и не начинает RUN от approve; owner deltas понятны и привязаны к предмету согласия.
- Prep не требует результат будущего потребителя; tree-проверки стоят перед публикацией и привязаны к публикуемым входам.
- Повторные тесты сокращены за счёт корректного выбора/reuse, а не снятия покрытия, отрицательных сценариев и независимого review.
- Wake/recovery/session-result не создают дубли и не теряют ожидающий ответ; если дефект не воспроизведён, это честно обозначено, а гипотетический новый механизм не выдан за необходимый.
- MD экспорт содержит реальные доступные timing каждого tool call, включая дочерние; отсутствующее/незавершённое явно обозначено.
- Каждый завершённый запуск оставил отчёт для продолжения. Финальный отчёт позволяет другой модели открыть именно проверенные ветки и провести независимое ревью.
