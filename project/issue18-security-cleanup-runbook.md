# #18 — очистка секретов из Git-истории: протокол

**Статус (2026-11-10): remote не переписан, ветки не удалены, репозиторий должен оставаться private.**

## Подтверждённые факты
- Перед созданием рабочей ветки #18 было 66 веток и 0 открытых PR. Проверка веток выявила и полностью слитые, и содержащие уникальные коммиты.
- На вершинах `archive/legacy-oac-agents-2026-09-11`, `chore/agent-model-upgrades`, `gpt`, `fix/pipeline-config-paths` в `config/opencode/opencode.json` остаются литералы пяти типов: Exchange X-API-Key, ITOP_TOKEN, Google OAuth client ID/client secret/refresh token. Это не просто ссылки на переменные окружения; действительность ключей не проверялась. Значения не копировать в отчёты.
- На текущем `main` этих пяти значений в данном файле нет. Сканирование каждого исторического объекта и вложения пока не выполнено.
- Ветки с уникальными коммитами (например, `feature/issue-60-gate-lifecycle` +26 и `feature/issue-63-pipeline-run-optimization` +65 относительно main) нельзя удалять без определения, какая работа нужна.

## Процедура
1. Зафиксировать полный список refs, теги, PR, форки, Actions artifacts, релизы и текущий SHA `main`; установить окно без параллельных push. Создать зашифрованную временную резервную копию (она всё ещё содержит секреты).
2. На **доверенной локальной машине**, а не на сервере OpenCode, создать полное зеркало: `git clone --mirror git@github.com:gest0r1/my-opencode.git`. Установить свежие `gitleaks`, `git-filter-repo` версии не ниже 2.47.
3. Из каталога зеркала выполнить `bash /path/to/security-history-audit.sh /absolute/private/report-dir`. Скрипт сохраняет refs/кандидатов на удаление и запускает redacted gitleaks по всем достижимым Git patches. Положительный результат — блокер. Вывод и отчёты не публиковать.
4. Дополнительно проверить **каждый достижимый исторический blob**, в том числе бинарные/архивные файлы, Git LFS; проверить PR refs, GitHub PR diff/comments, releases, workflow logs/artifacts, forks и caches. Gitleaks не гарантирует обнаружения нестандартных секретов.
5. Собрать `replacements.txt` по всем подтверждённым literal-значениям вне репозитория; `chmod 600 replacements.txt`. Этот файл сам содержит секреты — не коммитить, не прикладывать к issue и удалить после процедуры. Для целиком секретных файлов использовать `--invert-paths --path ...`, включая исторические переименования.
6. В зеркале выполнить `ISSUE18_APPROVE_LOCAL_REWRITE=yes bash /path/to/security-history-rewrite.sh /absolute/private/replacements.txt`. Запускается `git-filter-repo --sensitive-data-removal --replace-text`, удаление затрагивает все связанные предки/merge-коммиты и ref.
7. Повторить полный аудит, сравнить деревья сохраняемых веток с исходными за вычетом намеренно очищенных значений, проверить количество затронутых PR, теги, LFS и сохранность несмерженных изменений.
8. Подготовить **поимённый** список веток и тегов для переписывания и удаления с ожидаемыми прежними SHA. После freeze обновлять GitHub только с проверкой lease. **Не применять слепой `git push --force --mirror`**, особенно при наличии параллельной работы. `refs/pull/*` не перезаписываются push.
9. После remote update обратиться в GitHub Support по удалению PR refs, cached views и GC; передать first-changed-commits/affected-PR-count/LFS-orphans без значений секретов. Проверить старые SHA, очистить доступные GitHub артефакты, восстановить рабочие копии только из переписанной истории.
10. Включить GitHub push protection/secret scanning, локальные pre-commit проверки. Коллегам следует rebase/reclone, **не merge старую историю**, иначе значения снова появятся.

**До очистки и проверки остаточных рисков репозиторий нельзя делать публичным.** Очистка Git не отзывает скопированные токены. Если ротация невозможна — подтвердить ограничения IP/прав, мониторинг и отзыв доступных отдельных refresh-токенов; если риск остаётся существенным, сохранить private.
