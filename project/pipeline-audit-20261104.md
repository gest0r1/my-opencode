Календарный интервал **не является временем непрерывной работы**: включены ожидания владельца, паузы и независимые субагенты. Для сравнений с последующими прогонами нужны машинные timestamps начала/окончания команды, отдельно owner-wait, heavy-slot, live-slot и время вычисления моделей.

**Наблюдение по 0.6.7 PLAN:** 45 вызовов subagent содержали явный sessionID прежней сессии; в соответствующих 45 приложенных журналах все фактические Session ID были другими (0/45 совпадений). Всего 97 отдельных приложенных сессий. Таким образом, запрос «продолжи эту сессию» не обеспечил reuse; это не доказательство того, почему движок выбрал новую сессию. Новая сессия могла требовать повторного чтения контекста. Для плановых ревью свежая сессия предписана, но для уточнений ContextScout и StoryMapper передача sessionID вводила оркестратор в заблуждение.

**Отдельно, вне причин оптимизации:** в 0.6.6 зафиксированы последовательные повторные попытки SeniorStoryReviewer после 403. Учитывать их как дефект архитектуры конвейера или повод менять проверки нельзя; в отчётной телеметрии должна быть отдельная категория provider/model unavailable и восстановление после неё.

## 3. Какие тесты действительно определены в SeVami

Главный frozen профиль **release/fail-fast** содержит ровно 10 команд:
| Индекс | Реальная команда/категория | Характер нагрузки |
|---:|---|---|
| 0 | corepack pnpm run build | Полная сборка workspaces |
| 1 | corepack pnpm run typecheck | Полный typecheck |
| 2 | corepack pnpm run lint | Полный lint |
| 3 | vitest run packages | Тесты пакетов |
| 4 | vitest run apps/api | API-тесты |
| 5 | vitest run apps/worker | Worker |
| 6 | vitest run apps/telegram-bot apps/max-bot | Оба бота |
| 7 | vitest run scripts/testing | Тестовая инфраструктура |
| 8 | vitest run --root apps/web --config vitest.config.ts | Web |
| 9 | vitest run --config vitest.live.config.ts | Live PostgreSQL |

Все vitest-команды — через corepack pnpm exec; у всех --passWithNoTests=false. Источник: sevami/docs/testing/frozen-release-commands.json.

В обычном vitest.config.ts maxWorkers задаётся PIPELINE_MAX_WORKERS, testTimeout по умолчанию 10 секунд; в live config **maxWorkers=1, fileParallelism=false, testTimeout=30 секунд, hookTimeout=120 секунд, retry=0**. Live-проверки требуют базу и строгие доказательства происхождения контура. Это разумно для транзакционных инвариантов, но дорогой путь для проверки каждого небольшого изменения. Нельзя просто снять сериализацию или поднять таймаут: сначала выделить действительно конфликтующие live-кейсы, замерить setup/migrations/test и степень независимости фикстур.

Генератор scripts/testing/test-blocks.ts формирует карту соответствия исходников тестам, а docs/testing/impact-groups.json используется для выбора affected. В PLAN 0.6.7 замораживались 10 команд и **772 группы влияния**. Уже существуют coordinator_only, affected, cache PASS, snapshot и serial machine slots. Новая параллельная система тестирования не нужна.

Дополнительно release-candidate, install-check, smoke использовали scripts/testing/release-parity.sh → release-parity.ts с проверками identity, generated-check, docs-check, distribution, fresh/upgrade install, service-health. Это не часть десяти обычных fail-fast команд: стоимости надо учитывать раздельно. Реализованный CLI release-parity.ts (по проверенной версии main) содержит более 3000 строк; тестовое обеспечение этой системы само стало существенным источником доработок и требует анализа дублирующихся проверок до дальнейшего расширения.

## 5. Где терялось время: PLAN 0.6.7, по убыванию

1. **Прежде чем изучить текущую модель, сформировали новую.** Источник Issue #179 действительно описывает account+identifier+channel_link, несколько телефонов, merge, unlink; это не всё «выдумала модель». Однако выданная владельцу форма с рекомендованным «full» содержала последствия, не сопоставленные с работающими сценариями SeVami. Принятие предварительных опций было неверно интерпретировано как утверждение всей семантики. В 18:44 владелец указал: статус мастера — у той же identity, номер един, карточки не размножаются. Последовали переписывания stories, архитектуры и контрактов.
2. **Нарушена граница «сначала baseline и stories, потом архитектура».** Исходные механизмы регистрации, подтверждения номера, восстановления, отправки и идемпотентности не были полностью прочитаны до формулировки исключений. В 13:49 агент признал, что рисовал схему без запрошенного инвентаря ContextScout. В 16:07 владелец повторно остановил обсуждение уже утверждённой механики SET_PHONE и retries.
3. **Новые правила принимались как полноценные требования без проверки источника.** Примеры: два текущих номера у связанных клиентского и мастерского контуров; использование «Поделиться» как пути восстановления; отдельный журнал/очередь для синхронного master-share; повторная отправка при неоднозначном ответе вопреки действующему правилу. Часть из этого имела мотив в Issue, но не являлась согласованной дельтой поведения. Модель должна была противопоставить «текущий FACT — требование Issue — предлагаемая дельта», отметить конфликт, а не наращивать исключения.
4. **Слишком много циклов на одном наборе историй.** 27 StoryMapper и 25 SeniorStoryReviewer, 11 архитекторов, 12 техревьюеров, 7 ContractManager — это вызовы, не 25 независимых полноценный review cycles. Повторялись уже принятые решения и перепроверялись следствия удалённых гипотез. При этом полный ревью в качестве финального гейта остаётся необходим.
5. **Неверное делегирование и отсутствие подтверждённого resume.** ContextScout получил путь planning/drift/delivery-and-phone-inventory.md, тогда как запись разрешена только в planning/context-packet.md. Были два отказа, затем перезапуски; 45 запросов повторного sessionID в PLAN фактически породили новые ID. Входные Issue тела для StoryMapper были обрезаны; из-за этого первоначальные критерии писались по неполной информации.
6. **Одна полная PLAN-проба до исправления самого контракта.** 04.11 в 00:15–00:32 GateRunner затратил 17 агент-минут: 9/10 команд прошли, live остановился из-за RUNTIME_LOCK_MISSING. Это несовместимость preflight и live-proof, а не красный базовый тест. Следует проверять контракты test harness без полного запуска, а тяжёлый base-probe выполнять один раз.
7. **Финальное согласование недостаточно доказуемо.** В 07:04 владелец ответил «Ок» на конкретный вопрос о включении vitest.live.config.ts в scope для PLAN-пробы. В 07:23 агент выполнил plan-start, включая approve, **без видимого отдельного утверждения окончательного манифеста** с 25 WI. Это расходится с правилом независимого финального design-freeze approval.
8. **Готовность PLAN была объявлена вопреки собственному postcondition.** После plan-start github-issue-cli publish-plan отказал STORY_REVIEW_NOT_FULL_READY: последнее ревью историй содержало три carried findings. Отказ публикации должен был обнаруживаться до freeze/approve. Перенос технического замечания в RUN допускается по правилам, но сохранение готовности ревью и последующий отказ publish-plan означают противоречие контракта.
9. **Повторно задавались вопросы о ранее утверждённой механике.** Например, дедупликация запросов уже была в docs/features/referral.md, но спрашивалась заново; дополнительные варианты генерировали новые сценарии, которые пришлось затем отозвать.

### Что требовало утверждения владельца

Обязательно: новая пользовательская семантика по сравнению с фактическим baseline (объединение аккаунтов, роль/номер, takeover, доступ после потери телефона), изменение безопасности/прав владения, новое поведение при неопределённой отправке, существенное изменение обязательного объёма RUN, отдельное финальное утверждение замороженного PLAN, а также действительно новые правила данных/миграции с последствиями.

Не требовало отдельного выбора: сохраняемое действующее правило дедупликации; техническое объединение пересекающихся Issue в одну lane; выбор имен файлов, генератора, тестовой команды и локального пути внутри одобренных компонентов; исправление ошибочного scope/path при неизменном поведении; повтор уже принятого правила SET_PHONE без предложенной новой дельты; способ собрать контекст только из локального репозитория.

Форму для владельца нужно составлять **после** прочтения FACT/текущих тестов, показывая не возможные варианты фантазий, а реальные изменения и последствия. Вопрос с уже известным ответом не задавать повторно.

## 7. Исправленные предложения, порядок приоритета

### P0: исправить контракт планирования и критический путь

**P0-A. Current-behavior evidence gate до сторей и архитектуры.** На каждый меняющийся сценарий в одном месте: текущий route/handler → текущие данные/инвариант → действующие тесты/FACT → требование Issue → предлагаемая разница → необходимо ли решение владельца. Текущие правила по default «сохранить», а не «придумать замену». Источник Issue, конфликтующий с кодом, требует явно описать миграцию поведения. ContextScout собирает только пути/FACT, а не заново GitHub Issue; входной текст требований не обрезать.

**P0-B. Approval boundary по SHA.** Отдельные подтверждения: изменяемые baseline stories; только дельты изменённого архитектурой поведения; финальный freeze на точные manifest/WI/gates. Согласие на исправление пробного теста не становится согласием на весь freeze. plan-start технически готовит state, но не может записать owner-approved без отдельного события явного финального выбора. PLAN не запускает RUN: только явная команда RUN.

**P0-C. Машинная проверка заморозки.** plan-check обязан проверять согласованность approval SHA, отсутствующие blocking findings, готовность publish-plan, полные owner decisions, принадлежность тестов фазам, доступность фактических агентских разрешений, work item/paths/checks и доказуемость необходимых предусловий. FAIL нельзя маскировать «carried finding», если инструмент публикации затем отказывает.

**P0-D. Фазы и входы проверок.** Классы: tree / candidate / build-output / deployed-service; tree требует PASS перед публикацией, контрольные файлы не генерируются внутри publish. Независимые тесты — до кода; сценарии, зависящие от production entry, — после реализации; полная финальная проверка — один обязательный раз на зафиксированном дереве.

**P0-E. Пересмотреть test_preparation.** Не делать одну обязательную для всех lanes prep с требованиями, которые могут быть выполнены только после lanes. Замораживать реестр/рамку заранее, а заполнение и окончательную валидацию behavior-cells переносить в интеграционную стадию. В Plan DAG иметь машинную проверку фактической доступности фикстур на каждом шаге.

**P0-F. Тесты не должны проектировать продукт.** Не добавлять опасные/дорогие фазы боевого установщика только для удобства гейта автоматически. Сначала проверять, можно ли подтвердить инвариант black-box путем существующего installer, disposable DB, прошлой сборки и наблюдений. ## 7.1. Отдельная потеря: CoderAgent синхронно ждёт тесты

**Дополнительный разбор вложенных логов, 04.11.** Ранее пункт P1-A (affected/кэш) не решал полностью проблему: тестовое время заблокировано *внутри* CoderAgent, который делает foreground shell-вызов, а не просто находится в очереди GateRunner.

| Прогон | Число CoderAgent | Фактические тестовые shell-вызовы внутри CoderAgent | Суммарная длительность их сессий |
|---|---:|---:|---:|
| 0.6.6 (PLAN+RUN/продолжение) | 41 | 33 focus + 32 affected + 7 других тестовых = **72** | 1799 агент-мин |
| 0.6.7 RUN | 4 | 21 focus + 23 affected + 1 другой тестовый = **45** | 474 агент-мин |

Для 0.6.7 по четырём сессиям: behavior ledger 27 минут и 2 affected; test registry 27 минут и 3 affected (обе сессии параллельны); provision 254 минуты и 14 focus + 9 affected; rework 166 минут и 7 focus + 9 affected + 1 другой тест. Последние две сессии — **420 агент-мин**, 40 тестовых shell-вызовов. Это критический путь выпуска, но внутри 420 минут есть также программирование, чтение, диагностика и паузы.

**Сколько минут именно ждал CoderAgent:** по данным экспортов точно установить **нельзя**. В tool-блоках есть команды и результат, но **нет timestamps старта/конца каждого shell-вызова**; нельзя делить минуты сессии пропорционально количеству тестов, принимать 474 минуты за тесты или складывать параллельные сессии в wall-clock. Если GateRunner даёт duration команды только во внутреннем evidence JSON, время блокировки CoderAgent всё равно нужно измерять отдельно, с учётом machine-slot wait и восстановления после команды.

**Дополнение P0-G/P1-H: освобождение CoderAgent на долгих тестах, без обхода приёмки.**
1. CoderAgent делает изменения, быстрые локальные focus-итерации и публикует компактный checkpoint: diff/tree hash, изменённые файлы, WI, exact affected command, последние findings. По историческому P95 команда определяется как «длинная» (порог конфигурируется, например >60 сек), и тогда **CoderAgent не ждёт её foreground**.
2. Orchestrator передаёт long affected test в уже существующий GateRunner; GateRunner получает точный immutable snapshot/tree hash и возвращает доверенное evidence, принимаемое **тем же** stage-complete-cli. Не строить второй runner/cache.
3. Пока тест идёт, scheduler запускает независимые WI/lane/review с учётом разрешённых путей и machine slot; тот же CoderAgent не пишет в замороженный тестируемый снимок. Отсутствие другой runnable работы не создаёт искусственной параллельности.
4. PASS → автоматический stage-complete без возобновления дорогостоящего CoderAgent. FAIL → только структурированный failure summary и точный список затронутых тестов вернуть исполнителю в настоящую reused session, **если engine подтверждает reuse**; иначе запуск новой сессии по checkpoint, а не по всей истории. Повторный affected запуск после исправления; не перезапускать полный fail-fast.
5. Машинная телеметрия по каждой команде: queued_at, slot_acquired_at, started_at, finished_at, CoderAgent_blocked_ms, gate_cpu/wall_ms, heavy/live_slot_wait_ms, focus/affected/final, snapshot SHA, reuse, outcome. **Только после этого** считать точную экономию в минутах.

Этот пункт выше по приоритету, чем общая оптимизация review-циклов: он непосредственно освобождает критический путь и снижает бесполезное удержание дорогого агента. При этом запрос/выполнение gate и подтверждение PASS остаются обязательными: изменяется владелец ожидания, а не тестовое покрытие.

## 8. Метрики проверки результата

Для каждого RUN, в том числе остановленного: elapsed wall-clock, active work, owner wait, provider wait (только статистика), heavy/live slot wait, время установки зависимостей, длительность каждой gate command, число команд реально запущенных/переиспользованных, число source-changing repairs, число повторов по defect_class, число опубликованных candidate SHA, возвратов после publish, permission denials, контекстных recovery, request-reuse vs actual-reuse, токены/стоимость по роли и модели с кэшем отдельно.

Для PLAN отдельно: число неразрешённых вопросов, число вопросов уже покрытых FACT, количество cycles/агентов до baseline approval, число изменённых после approval user scenarios, повторные ContextScout, проверка source Issue body полноты, число недопустимых дочерних artefact_path, число финальных preflight ошибок и время пробного полного гейта.

**Критерий успеха:** меньше wall-clock и total paid tokens при сохранении независимой приёмки и неизменного/более полного доказательства каждого бизнес-инварианта. Нельзя оптимизировать только число ревью или только CPU без проверки утечки дефектов на owner acceptance.
